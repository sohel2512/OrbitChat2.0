     8→# REA
     9→
    10→Use REA when a claim depends on a shipped binary or package, decompilation,
    11→requested runtime evidence, or comparison with
    12→behavior not established by available source. For ordinary analysis of a
    13→complete source repository, use normal repository tools and do not run REA
    14→readiness or provider commands.
    15→
    16→## Connect only when needed
    17→
    18→Installing this skill supplies instructions; it does not register the REA MCP
    19→server, install analysis engines, or add tools to an already-running agent.
    20→The exception is a Claude Code or Codex plugin install: the plugin bundles
    21→this skill and registers its own `rea` server, outside the state that
    22→`rea setup` and `rea doctor` manage.
    23→
    24→If REA tools are available and their registration is not known to be stale,
    25→proceed directly to the target. Do not run diagnostics or setup before every
    26→investigation. Use the connected server's actual tool list and input schemas;
    27→a skill installed from repository main may describe capabilities absent from
    28→an older npm release. Keep complete inline Evidence when that server does not
    29→advertise retained references.
    30→
    31→If tools are absent, a call is blocked by the client, or a required provider is
    32→unavailable, read [connection and recovery](references/connection-and-recovery.md).
    33→Diagnose the observed blocker, continue useful supported work, and resume the
    34→original task after repair. Client approval, shell PATH, registration and engine
    35→availability have different remedies; avoid repeating setup for all of them.
    36→If the host times out without a REA result, do not repeat the unchanged call or
    37→assume work stopped. Read the recovery guide's deadline distinction before retrying.
    38→If the MCP connection drops, retry that call once only when it is safe to
    39→repeat or known not to have started. If it may already have changed the
    40→target, or it fails again, tell the user and ask them to restart the MCP
    41→client. If REA could not start its connection, retry once, then tell the user
    42→and ask them to restart the MCP client. Do not retry a startup failure that
    43→returns the same unchanged result. For plugin installs, follow
    44→[plugin recovery](references/connection-and-recovery.md#rea-installed-as-a-client-plugin).
    45→For setup-owned registrations, run `rea doctor` when REA could not start
    46→or tools stay missing after that restart. For `cleanup_incomplete`, a retryable
    47→capacity limit, or `configuration_invalid`, follow the recovery guide's ladder
    48→before asking for a restart. Read that guide before a second repair attempt.
    49→
    50→Choose the installation owner before repairing registration. Plugin installs use
    51→[plugin recovery](references/connection-and-recovery.md#rea-installed-as-a-client-plugin);
    52→only setup-owned registrations use the guide's
    53→[registration repair plan](references/connection-and-recovery.md#repair-registration-when-needed).
    54→A plugin-only doctor result of `missing` does not call for `rea setup`.
    55→
    56→REA setup never installs or upgrades Node.js, npm, Homebrew, Java, Ghidra, IDA,
    57→JADX, Kuna, Binwalk, or Unblob. Use existing prerequisites; do not install unrelated
    58→software to repair MCP registration. For an unsupported client, use manual stdio
    59→registration with an existing installation’s absolute runtime and entry script, or continue through the CLI.
    60→
    61→A concrete CLI fallback for an operator-supplied JavaScript tree or ASAR is:
    62→
    63→```bash
    64→npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json
    65→```
    66→
    67→No MCP registration or native engine is required. Read the returned Evidence,
    68→graph, limitations, and unknowns with the same care as an MCP result; the CLI
    69→returns the Evidence record directly. This fallback does not establish that
    70→MCP is configured. Native CLI tasks still require their selected engine.
    71→Prefer an existing `rea` CLI. When none is installed and REA package acquisition
    72→is within the authorized scope, use `npx -y rea-agents@latest` in its place from a
    73→trusted directory outside the target project, with absolute target paths. Managed
    74→setup binds the current installation directly; retain its runtime and package
    75→cache entry, or restore that installation before repairing its registration.
    76→For setup-owned registration, configuration repair starts with a read-only setup plan; show paths, backups and
    77→skill replacement before applying authorized changes. Preserve existing approval
    78→and target-execution boundaries.

    80→## Route the target first
    81→
    82→Choose the first tool from the target the user supplied. Use `open_binary` for
    83→active-target native or archive workflows; target-free tools take their own
    84→explicit path or endpoint and do not need it.
    85→
    86→- ASAR or extracted JavaScript/Electron tree:
    87→  `analyze_javascript_application`.
    88→- Archive/package member inventory (ZIP/APK/IPA/MSIX/AppX, DMG, or a PyInstaller
    89→  executable): `open_binary` with the supplied local path; use `inspect_artifact`
    90→  when its graph and findings help answer the question. A PyInstaller CArchive
    91→  is the application layer; the bootloader is only the native prefix. Start with
    92→  `detail: "summary"` for large inventories, then use retained inventory views
    93→  for selected member fields/pages. A complete small inventory can cost less
    94→  than extra calls and schemas. Runtime options are metadata, not files.
    95→  Compact delivery still inventories and hashes members. See the
    96→  [Python packaged applications guide](https://github.com/morluto/rea/blob/main/docs/python-packaged-applications.md).
    97→- Bun `--compile` executable: `open_binary`, then `inspect_artifact`; the Bun
    98→  module graph is the application layer. Extract stored modules and analyze the
    99→  JavaScript. See [Bun standalone executables](https://github.com/morluto/rea/blob/main/docs/bun-standalone.md).
   100→- Deno `deno compile` executable: `open_binary`, then `inspect_artifact`; the
   101→  embedded virtual filesystem is the application layer. Extract stored files and
   102→  analyze compatible JavaScript. Environment-file values and CA certificate bytes
   103→  are retained in local Evidence with their counts and byte lengths. The npm
   104→  snapshot length is reported and not decoded, and the executable is not run. See
   105→  [Deno compile executables](https://github.com/morluto/rea/blob/main/docs/deno-standalone.md).
   106→- Apple app plist, Interface Builder, asset catalog, or keyed archive resources:
   107→  `open_bundle_resources`, then the selected resource tool. This does not
   108→  require `CFBundleExecutable` or a deep provider. Resource sessions have no
   109→  executable digest or binary snapshot; use `open_binary` for native code.
   110→- Android APK code, classes, methods, or incoming references:
   111→  `inspect_android_package`, then focused Android tools when advertised.
   112→  Archive member inventory still uses the archive route above.
   113→- Managed PE/CLI assembly: `inspect_managed_artifact`.
   114→- Firmware image: `inspect_firmware_regions` when advertised. Use
   115→  `extract_firmware` when extraction is requested, with a caller-selected new
   116→  absolute output directory. These tools use caller-supplied Binwalk/Unblob on
   117→  Linux; see the [firmware guide](https://github.com/morluto/rea/blob/main/docs/guides/firmware/firmware-analysis.md).
   118→- ESP32-family app or bootloader image (`0xE9` magic): `inspect_artifact`
   119→  without a provider; see the ESP section of `references/native-and-artifacts.md`.
   120→- .NET NativeAOT PE/ELF: native Ghidra analysis. Native code can yield pseudocode;
   121→  consult the NativeAOT workflow in `references/native-and-artifacts.md` for
   122→  optional metadata recovery and its supported host/layout boundary.
   123→- Native program behavior, live calls, instrumentation, or command-run effects:
   124→  choose the matching [native runtime workflow](references/runtime-observation.md#native-runtime-questions).
   125→  `open_binary` and `trace_native_values` establish static facts; they do not
   126→  observe execution. Runtime tools have distinct launch, attach, mutation and
   127→  cleanup effects, and do not require a preliminary static session unless their
   128→  own contract says so.
   129→- User-owned browser page already open: `list_browser_targets`.
   130→- Passive traffic capture of a SPA: the default scope is the page's own origin,
   131→  and data APIs usually live on another origin. Discover API origins from
   132→  absolute URLs in loaded bundles or script text via JavaScript analysis tools
   133→  (another passive capture without those origins still scopes to the page
   134→  origin, and `completeness.excluded` counts lack URLs). Pass both the page
   135→  origin and those API origins in `allowed_origins` — the list replaces the
   136→  default scope — and read `completeness.excluded` before reporting that an
   137→  API is absent. For long captures with body shapes, use
   138→  `export_evidence_bundle` instead of expecting an inline result.
   139→- Browser action the agent must perform (click, type, navigate):
   140→  `capture_browser_scenario` with declared actions. See
   141→  [runtime observation](references/runtime-observation.md) for connect/launch
   142→  and the focused follow-up browser tools.
   143→- Agent environment (AgentEnv bundle) of a web application: read
   144→  [environments](references/environments.md) before recording; it records with
   145→  `capture_browser_scenario` and writes the bundle with `export_environment_bundle`.
   146→- Task for a desktop application's exported environment, from a
   147→  `capture-desktop-application` folder: read
   148→  [desktop application tasks](references/environments.md#tasks-for-a-desktop-application-environment).
   149→- Environment of a Linux desktop app with a task, from a request such as
   150→  "build me an Inkscape environment where the agent changes a poster's
   151→  headline": read [desktop builds](references/desktop-build.md). You drive the
   152→  app on a build computer from `start_build_computer`, then export and witness.
   153→- Fiddler Everywhere traffic or a native `.saz` capture: read the
   154→  [Fiddler workflow](references/runtime-observation.md#fiddler-everywhere-traffic-debugging).
   155→  Inspect saved SAZ with `inspect_web_network_capture` and `format: "saz"`;
   156→  connect Everywhere's separate MCP server for live traffic.
   157→- Retained HAR/SAZ/native mitmproxy/aioquic qlog capture: `inspect_web_network_capture`. Select
   158→  original record ordinals when useful; inspect producer fields and byte/number
   159→  sidecars without fetching recorded URLs or claiming live attribution. HAR/SAZ/qlog
   160→  old-generation heap is `REA_CAPTURE_DECODER_OLD_GENERATION_MIB` (default 192 MiB,
   161→  floor 8, maximum 16384), set where REA starts. Host memory and `NODE_OPTIONS` do not
   162→  raise it. See
   163→  [historical captures](https://github.com/morluto/rea/blob/main/docs/guides/web/web-network-captures.md) for the exact upstream
   164→  profile and credential exclusions. Qlog support starts with aioquic 1.5.0
   165→  JSON 0.3; stream coverage and endpoint loss declarations do not recover bodies
   166→  or establish network loss. Prefer detail summary, then kind qlog trace/stream
   167→  pages; select one trace, stream ID and direction for contribution/range pages.
   168→  Facts retain all-recorded-events-before-selection scope. Other qlog layouts
   169→  and PCAP correlation are unsupported.
   170→- User-owned Electron runtime already open: `list_electron_targets`. Before an electron-main Inspector attempt, check packaged fuses with `inspect_electron_fuses`; disabled `EnableNodeCliInspectArguments` means the app ignores `--inspect`.
   171→- Packet-field discovery: `inspect_packet_fields` searches installed protocols
   172→  and field names/types before choosing fields for `inspect_packet_capture`.
   173→  Query/page the relevant records; registrations do not establish observed traffic.
   174→- Recorded packet captures: `inspect_packet_capture` with selected TShark fields,
   175→  display filters and decode-as rules. Requires Linux, util-linux prlimit and
   176→  TShark 4.x on an absolute `PATH` entry or via the optional absolute
   177→  `REA_TSHARK_COMMAND` override; see
   178→  [capture guide](https://github.com/morluto/rea/blob/main/docs/guides/data/packet-captures.md).
   179→  Packet limits count input packets before filtering. Output defaults to 50 matching
   180→  frames; use `match_offset` / `match_limit` for later pages, or explicit null
   181→  limit for complete matching output. Preserve the source digest across pages.
   182→  This does not perform live capture.
   183→  For address/DNS/SNI/protocol summaries use `inspect_pcap_capture` with MCP
   184→  detail summary, then retained kind pcap pages. Requires Wireshark 4.x tshark
   185→  and capinfos, with Linux prlimit or Windows Job Objects; see
   186→  [packet summaries](https://github.com/morluto/rea/blob/main/docs/guides/data/pcap-analysis.md).
   187→  Select an exact DNS question for address pages; page exhaustion does not prove
   188→  network completeness. This reads recordings and does not acquire traffic.
   189→- Decoder discovery: `inspect_signal_decoders` searches installed decoder IDs
   190→  or selected decoder help, including channels and options. Query and page the
   191→  relevant details before choosing settings; this does not scan hardware.
   192→- Recorded logic/signal traces: `decode_signal_recording` with explicit decoder,
   193→  channel and protocol settings. On Linux with util-linux prlimit, supply sigrok-cli 0.7.2 through
   194→  `REA_SIGROK_COMMAND`; see [recording guide](https://github.com/morluto/rea/blob/main/docs/guides/signals/signal-recordings.md).
   195→  Output defaults to 50 literal lines; select annotation classes and page with
   196→  `line_offset` / `line_limit`, or explicit null for all remaining output.
   197→  Window counts are display lines, not annotations or samples. Preserve source digests across pages.
   198→  This reads existing files; it does not acquire hardware signals.
   199→- Explicit local WebAssembly artifact: `inspect_wasm_artifact`. Supply WABT 1.0.42
   200→  through `REA_WABT_BIN_DIRECTORY`; retain exact byte/tool identity and decoded WAT.
   201→  Select JavaScript glue and candidate paths explicitly and preserve URL/path
   202→  ambiguity. No implicit fetch or target execution; WAT is not original source.
   203→  See the [WASM guide](https://github.com/morluto/rea/blob/main/docs/guides/wasm/wasm-artifacts.md).
   204→- Explicit local Android APK (or ZIP/AAB) signing: `inspect_apk_signature`.
   205→  Prefer its summary or selected signer/digest/lineage page; retain complete
   206→  Evidence and use `inspect_analysis_view` kind `apk-signature` for follow-ups.
   207→  Reports which schemes are present (v1 JAR, v2, v3, v3.1), each signer's
   208→  certificate SHA-256 fingerprint (v1 included, from its PKCS#7 block), v3 key-rotation lineage, source stamp, and
   209→  whether each signed digest still matches the bytes (self-consistency). This
   210→  is identity and integrity, not a trust or authenticity verdict.
   211→  See the [APK signature guide](https://github.com/morluto/rea/blob/main/docs/apk-signature.md).
   212→- Explicit local EVM bytecode carrier: `inspect_evm_interface` with caller-selected
   213→  `raw` or `hex` encoding. The owned worker deadline is `timeout_ms` (default
   214→  30000 ms, range 1..2147483647, next call). It does not raise the fixed byte,
   215→  address-space, or CPU allowances. Preserve carrier/decoded digests and treat selectors,
   216→  argument strings and mutability as inferred candidates; this performs no chain
   217→  lookup or target execution. For the complete inferred interface without hex or
   218→  duplicate stdout, discover support and select `detail: "summary"`; complete
   219→  Evidence stays retained under its original identity. Use the returned
   220→  `parent_evidence_id` for exact function or `bytecode_hex`/stdout/stderr pages.
   221→  Candidate coverage does not establish interface completeness. See the
   222→  [EVM bytecode guide](https://github.com/morluto/rea/blob/main/docs/guides/evm/evm-bytecode.md).
   223→- Embedded Go compiler, module, build-setting metadata, or static `(ptr, len)`
   224→  string literals: `inspect_go_binary` with the explicit local file (pass
   225→  `include_string_literals: true` and optional `max_string_literals` for bounded
   226→  inferred static string-header recovery, and page retained rows with
   227→  `inspect_analysis_view` kind `go` collection `string_literals`). This built-in
   228→  target-free inspection requires no Go installation or disassembler. Preserve
   229→  raw module bytes and source ranges; absent metadata does not prove a binary is
   230→  not Go, static string recovery excludes compiler-inlined stack or immediate
   231→  strings, and unparsed text records remain explicit. See the
   232→  [Go binary guide](https://github.com/morluto/rea/blob/main/docs/guides/native/go-binaries.md).
   233→- Embedded CUDA/HIP code objects: `inspect_gpu_code_objects`; inventory targets
   234→  first, then decode selected payloads and query retained GPU Evidence.
   235→- Bundled GGUF or safetensors model declarations: `inspect_model_artifact`
   236→  with the explicit local file. Default header hashing leaves full-file identity
   237→  unknown; `hash: "full"` additionally reads all weights for SHA-256. MCP returns
   238→  retained summaries; optional `view` selects one page in the initial call. Use
   239→  `inspect_analysis_view` kind `model-artifact` for
   240→  batched metadata keys, tensor names or type totals, selected fields and pages.
   241→  Preserve header-scoped indices and array preview omissions; do not infer model
   242→  behavior from declared architecture or tensor types. See the
   243→  [model file guide](https://github.com/morluto/rea/blob/main/docs/model-artifacts.md).
   244→- Unity IL2CPP names, member owners and string literals from `global-metadata.dat`:
   245→  `inspect_il2cpp_metadata` with the explicit local file; MCP defaults to compact
   246→  counts. Query sections, images, types, methods, fields, properties, events,
   247→  parameters or string_literals through `inspect_analysis_view`
   248→  with the returned `parent_evidence_id`, using exact filters, batch indices and
   249→  selected fields. Parameters accept `method_indices`, avoiding a scan of all
   250→  parameter pages. Missing collections in historical Evidence remain unknown.
   251→  Versions 24, 27, 29, 31 and 39; no Unity, IL2CPP
   252→  binary or disassembler is run. Unrecognized magic (possibly encrypted) and
   253→  other versions are unsupported. Optional matching `binary_path` enables static native addresses and type references; query `method_addresses` with indices or addresses/states, preserving every shared-body method and both artifact identities. Without a linked binary native counts remain unknown. Byte-pattern fallback is inferred; no runtime behavior or same-build pairing is proved. See the
   254→  [IL2CPP metadata guide](https://github.com/morluto/rea/blob/main/docs/il2cpp-metadata.md).
   255→- Embedded cargo-auditable Rust dependency metadata: `inspect_rust_binary`
   256→  with the explicit local ELF, PE, or thin Mach-O file. This built-in
   257→  target-free inspection requires no Rust installation or disassembler. Preserve
   258→  package order, dependency indices, and the section file range. A missing
   259→  `.dep-v0` section is null metadata, not proof the binary has no dependencies.
   260→  A rustc commit hash is an inference from a read-only `/rustc/<40-hex>/` path.
   261→  For selected crates, use `view: {collection: "packages", names: [...],
   262→  fields: ["name", "version", "source"]}` on the first call; explicitly include
   263→  `dependencies` for direct index references. Use `detail: "summary"` for counts
   264→  and ranges, or retained `inspect_analysis_view` Rust package/edge pages for
   265→  subsequent filters. Keep the complete parent Evidence accessible; CLI compact
   266→  delivery requires `--evidence_output`.
   267→  See the
   268→  [Rust binary guide](https://github.com/morluto/rea/blob/main/docs/rust-binaries.md).
   269→- PE Authenticode certificate table: `inspect_pe_certificates` with the explicit
   270→  local PE32/PE32+ file. This built-in target-free inspection requires no
   271→  Windows SDK. Preserve WIN_CERTIFICATE ranges, types, payload SHA-256, and
   272→  PKCS#7 signer/X.509 identity fields, including `subject_key_identifier_hex`
   273→  when the signer uses that form. A missing security directory is observed
   274→  absence of that table, not proof the image is unsigned in every catalog sense.
   275→  Signatures are not verified. See the
   276→  [PE certificate guide](https://github.com/morluto/rea/blob/main/docs/pe-certificates.md).
   277→- PE import and delay-load tables: `inspect_pe_imports` with the explicit
   278→  local PE32/PE32+ file. This built-in target-free inspection requires no
   279→  Windows SDK. Preserve DLL names, named and ordinal functions, ILT/IAT RVAs,
   280→  delay-load descriptors, and the pefile import hash of the standard import
   281→  table. A missing import directory is observed absence of that table, not
   282→  proof the image never imported APIs through another table. Bound snapshots
   283→  and loaded IAT contents remain unobserved. See the
   284→  [PE import guide](https://github.com/morluto/rea/blob/main/docs/pe-imports.md).
   285→- Windows Shell Link shortcuts: `inspect_windows_shortcut` with the explicit
   286→  local `.lnk` file. This built-in target-free inspection requires no Windows
   287→  SDK or COM. Preserve header flags and FILETIMEs, IDList items, LinkInfo
   288→  volume and network names, StringData arguments and icon location, ExtraData
   289→  signatures, and Tracker droid facts labelled derived. Unknown IDList items
   290→  and ExtraData signatures stay raw with SHA-256. The target path is not
   291→  resolved or executed. See the
   292→  [Windows shortcut guide](https://github.com/morluto/rea/blob/main/docs/guides/native/windows-shortcut.md).
   293→- PE TLS callbacks and load configuration: `inspect_pe_load_config` with the
   294→  explicit local PE32/PE32+ file. This built-in target-free inspection requires
   295→  no Windows SDK. Preserve callback VAs as strings with their RVA, file offset
   296→  and section, and the size-covered security cookie, SafeSEH, CFG,
   297→  EH-continuation and XFG fields. Guard-flag mitigation claims are inferred
   298→  linker declarations, not proof of enforcement. A missing directory is observed
   299→  absence of that declaration. See the
   300→  [PE load configuration guide](https://github.com/morluto/rea/blob/main/docs/pe-load-config.md).
   301→- ELF, PE, and Mach-O hardening: `inspect_binary_hardening` with the explicit
   302→  local file. This built-in target-free inspection requires no pwntools or other
   303→  host tool. One image per Mach-O slice. Each property is `enabled`, `disabled`,
   304→  `partial`, `unknown`, or `not_applicable`, with the header field or import
   305→  behind it. A missing stack-protector or fortify import is `unknown`, not
   306→  proof the protection was omitted. Authenticode and Mach-O code signatures
   307→  report presence, not validity. Hardened runtime stays unknown and names
   308→  `inspect_signature`. The image is not executed. See the
   309→  [binary hardening guide](https://github.com/morluto/rea/blob/main/docs/binary-hardening.md).
   310→- ELF note tables: `inspect_elf_notes` with the explicit local ELF32/ELF64
   311→  file. This built-in target-free inspection requires no disassembler. Preserve
   312→  PT_NOTE and SHT_NOTE ranges, owners, types, descriptor SHA-256, and GNU
   313→  build-id or ABI-tag fields. A missing table is observed absence of those
   314→  declarations, not proof the image never carried notes. See the
   315→  [ELF notes guide](https://github.com/morluto/rea/blob/main/docs/elf-notes.md).
   316→- Code that runs before `main` or at exit in ELF or Mach-O:
   317→  `inspect_native_initializers` with the explicit local file (and
   318→  `architecture` for a universal Mach-O). This built-in inspection requires no
   319→  disassembler. Preserve slot and target addresses, the `resolution` of each
   320→  entry, and its limitations. An `unresolved` slot is not a zero pointer, and a
   321→  missing table is not proof that no constructor exists. See the
   322→  [initializer guide](https://github.com/morluto/rea/blob/main/docs/guides/native/native-initializers.md).
   323→
   324→- ELF unwind function ranges: `inspect_elf_unwind_ranges` with the explicit
   325→  local ELF32/ELF64 file. This built-in target-free inspection requires no
   326→  disassembler. Preserve FDE start, end, size, containing section, exact
   327→  symbol name, CIE index, LSDA, and personality. Page with `offset` and
   328→  `limit`. A missing `.eh_frame` is observed absence of that declaration,
   329→  not proof the image has no functions. `.debug_frame` is reported present
   330→  or absent and is not decoded. CFA instructions are counted and not
   331→  evaluated. See the
   332→  [ELF unwind ranges guide](https://github.com/morluto/rea/blob/main/docs/guides/native/elf-unwind-ranges.md).
   333→- Apple `.ips` crash reports: `inspect_apple_ips` with the explicit local
   334→  file. This built-in target-free inspection requires no Xcode, atos, or
   335→  pwntools. Preserve first-line metadata, `bug_type` as a string, process and
   336→  exception facts, lossless integer registers, usedImages UUIDs, and
   337→  documented classification matches. Only `bug_type` `"309"` yields a crash
   338→  body; other types, including `"288"` stackshots, return no crash result.
   339→  Opened Mach-O and dSYM UUID joins remain unobserved. See the
   340→  [Apple IPS guide](https://github.com/morluto/rea/blob/main/docs/apple-ips.md).
   341→- Linux kernel module metadata: `inspect_kernel_module` with the explicit local
   342→  ELF32/ELF64 relocatable file. This built-in target-free inspection requires
   343→  no Linux host or `modinfo`. Preserve `.modinfo` key order and duplicate keys,
   344→  `__versions` CRC hex, section file ranges, and the appended signature
   345→  trailer's PKCS#7 SHA-256. A missing section is observed absence when section
   346→  names are known, not proof the module never carried that metadata.
   347→  `struct module` is not decoded. The signature is not validated. gzip, xz, and
   348→  zstd containers are unsupported; decompress into a separate file with an
   349→  external codec utility, then inspect the decompressed `ET_REL` image. See the
   350→  [kernel module guide](https://github.com/morluto/rea/blob/main/docs/kernel-modules.md).
   351→- Linux kernel version and build config (`CONFIG_*` options such as
   352→  `CONFIG_SECURITY_SELINUX`): `inspect_kernel_build_config` with the explicit
   353→  local `vmlinux`, raw `Image`, x86 `bzImage`, or `configs.ko`. This built-in
   354→  target-free inspection requires no Linux host or `extract-ikconfig`. Preserve
   355→  the banner version, config SHA-256, option count, and value kinds; use `name`
   356→  for one option. An `IKCFG_ST` string is a config only with a valid gzip member
   357→  and `IKCFG_ED`. An absent config may mean the kernel was built without
   358→  `CONFIG_IKCONFIG`. Non-gzip payloads are unsupported; decompress externally,
   359→  then inspect the result. See the
   360→  [kernel build config guide](https://github.com/morluto/rea/blob/main/docs/guides/native/kernel-build-config.md).
   361→- CPython 3.7–3.13 `.pyc` header, nested marshal code objects and bytecode
   362→  identity: `inspect_python_pyc` with the explicit local file. This built-in
   363→  target-free inspection requires no Python installation. Preserve magic,
   364→  PEP 552 hash or mtime/size, nested names, and bytecode SHA-256. Bytecode is
   365→  not decompiled, and a decoded header does not prove the matching `.py` is
   366→  present. See the
   367→  [CPython pyc guide](https://github.com/morluto/rea/blob/main/docs/python-pyc.md).
   368→- Erlang BEAM IFF container: `inspect_erlang_beam` with the explicit local
   369→  `.beam` file. This built-in target-free inspection requires no Erlang
   370→  installation. Preserve chunk names, atom order, export/import/lambda tables,
   371→  and the Code header. For selected facts, prefer `detail: "summary"` plus a
   372→  `beam` view (collection, names/indices, fields and paging), retaining the full
   373→  Evidence. CLI summary requires `--evidence_output`. Missing table counts stay
   374→  null; decoded empty tables count zero. Bytecode is not executed. See the
   375→  [Erlang BEAM guide](https://github.com/morluto/rea/blob/main/docs/erlang-beam.md).
   376→
   377→- Explicit local SQLite database snapshot: `inspect_sqlite_database`. Inspect
   378→  with Node.js 24.x >=24.15 or 26+ providing native SQLite limits. Read schema
   379→  first (compact inventory by default), or select an exact ordinary table
   380→  and `columns` when rows are needed. Defaults are selected-table schema and
   381→  20 rows; request `schema_scope: "database"` for the complete stored schema. Preserve both database and existing sibling WAL identity; row samples
   382→  report truncation and have unspecified order. Use a quiescent snapshot rather
   383→  than assuming a live database/WAL pair was copied atomically. See the
   384→  [SQLite guide](https://github.com/morluto/rea/blob/main/docs/guides/data/sqlite-databases.md).
   385→- Explicit Linux ELF file for offline layout, symbols, relocations or static
   386→  mitigation evidence: `inspect_binary_layout`. This target-free operation uses
   387→  caller-supplied pwntools without opening a disassembler database. Preserve its
   388→  raw locations and inference/coverage limits; see the
   389→  [offline binary guide](https://github.com/morluto/rea/blob/main/docs/guides/native/binary-diagnostics.md).
   390→- Supplied Linux x86-64 ELF core: `inspect_recorded_crash`. Read every recorded
   391→  thread, raw note and source-bound register without opening a live target.
   392→  Historical PIDs do not select live processes. Request `include_debugger_context`
   393→  only when core-only mapping candidates help; see the
   394→  [recorded crash guide](https://github.com/morluto/rea/blob/main/docs/guides/native/recorded-crashes.md).
   395→- PE resource type/name/language trees and static icon group references:
   396→  `inspect_pe_resources` with an explicit path. This portable operation requires
   397→  no active target or engine; opaque payloads retain file ranges and SHA-256.
   398→- PE export directories and ELF dynamic-symbol exports: `inspect_native_exports`
   399→  with an explicit path; portable, no active target or engine.
   400→- Native executable, library, or analysis database: `open_binary`, then
   401→  use focused analysis tools directly; call `binary_overview` when metadata or
   402→  inventory context is useful and available from the selected provider.
   403→
   404→For an existing IDA MCP configuration, use `open_binary` with the original
   405→input binary and `provider_id: "ida"`; do not pass an `.idb` or `.i64` database.
   406→The legacy attached profile binds the already-open GUI input by SHA-256 and
   407→leaves its database open. The modern headless profile creates and closes an
   408→owned private database without saving. Installation and registration reuse
   409→[mrexodia/ida-pro-mcp](https://github.com/mrexodia/ida-pro-mcp); see the
   410→[IDA provider guide](https://github.com/morluto/rea/blob/main/docs/providers/ida-provider.md).
   411→For migration to the separate native IDA MCP plugin, follow the guide's
   412→[legacy attached migration](https://github.com/morluto/rea/blob/main/docs/providers/ida-provider.md#migrate-a-legacy-attached-registration).
   413→Replace the upstream registration explicitly; modern mrexodia tools are not the
   414→native profile. Native attachment preserves the database but does not provide
   415→direct callers; check session availability and the guide's verification limits.
   416→Proceed directly to `analyze_function`, pseudocode, or function/string searches
   417→after opening; IDA does not supply `binary_overview`. Consult session availability
   418→when composing broader workflows. Modern direct callers and unsupported dossier
   419→facets remain unknown; live IDA results are not replayed from snapshots.
   420→
   421→With `REA_KUNA_COMMAND` configured, `provider_id: "kuna"` answers procedure
   422→lists, lookups, pseudocode, assembly and `analyze_function` from Kuna's cached
   423→whole-program export. Callers/callees use a separate body-free graph shared by
   424→the session; `xrefs` returns exact-address incoming sites and filters forwarding
   425→aliases. These queries and inventory lookups do not trigger a C export. Indirect
   426→targets remain unknown and can make relationship coverage partial. Reference
   427→caches expire on close; a fresh CLI process repeats the native reference walk.
   428→Typed references, CFG, raw-memory tools and annotations remain unsupported. A cold first
   429→answer can come from a single-function run (its limitations say so); assembly
   430→waits for the export. For pseudocode and assembly, `raw_result.source` names the
   431→cached `.c`/`.asm` file and byte span, which you may search directly instead of
   432→calling per function. See the
   433→[Kuna provider guide](https://github.com/morluto/rea/blob/main/docs/kuna-provider.md).
   434→
   435→If the user says only "my app" without a name, path, or target already selected
   436→for this task, ask which app before searching for artifacts. Paths in unrelated
   437→saved reports and nearby test fixtures do not select the user's target. Resolve
   438→an actual human-readable app name to one clear installed artifact when possible;
   439→ask when matches are ambiguous. Never choose an example app on the user's behalf.
   440→
   441→In a target-free session, use `open_binary` to bind any archive/package or
   442→native target whose analysis tool operates on the active target. Do not call an
   443→unadvertised tool; inspect `binary_session` with `{}` and its
   444→`result.tool_availability` for availability reasons and remediation. Expand each
   445→group's `names` into entries, inheriting the inventory-level client requirements
   446→unless the group overrides them. The grouped name union is the complete tool
   447→inventory; use `tools/list` for canonical tool schemas. The default summary keeps
   448→each provider candidate's availability and target-support status, code and
   449→reason; `omitted_fields` lists what it leaves out. Request `{"detail": "complete"}`
   450→only when you need an unavailable candidate's remediation, provider
   451→diagnostics, candidate capability sets, or tool surface, effect and annotation
   452→flags; in those closed flag vocabularies, listed
   453→flags are true and omitted known flags are false. Provider candidate facts
   454→describe possible providers, while top-level session capabilities describe the
   455→current route and `analysis_provider_binding` names the selected provider. Do
   456→not treat those scopes as interchangeable.
   457→
   458→For editable Ghidra analysis that must survive a later agent process, select
   459→the [owned Program checkpoint workflow](references/native-and-artifacts.md#continue-editable-ghidra-analysis-across-processes)
   460→before making metadata edits. It is separate from Evidence/Unknown persistence.
   461→
   462→For a Ghidra startup timeout on a large native target, follow
   463→[deadline recovery](references/native-and-artifacts.md#ghidra-startup-deadline-recovery)
   464→before abandoning deep analysis or repeating the same cold import. The default
   465→330 seconds can be changed for new startup attempts through
   466→`update_analysis_settings` using `ghidra.startup_timeout_ms`. Changing the
   467→server's launch environment instead requires a new REA process.

   469→## Work summary-first
   470→
   471→Start with the default result and use its inline Evidence and graph context.
   472→For a JavaScript application or ELF layout whose size is unknown or large,
   473→call `analyze_javascript_application` or `inspect_binary_layout` with
   474→`"detail": "summary"`, then inspect the retained `parent_evidence_id` with
   475→`inspect_analysis_view`. Over MCP, `analyze_function` is summary-first without
   476→a flag: its default reply is the summary, and the complete dossier stays
   477→retained under `parent_evidence_id` for facet paging. Pass that ID as a
   478→`retained-evidence` reference to `compare_functions`, or inside
   479→`match_native_functions` `left_observations`/`right_observations` or
   480→`build_call_path.functions`; request `"detail": "complete"` only when the
   481→dossier must travel inline.
   482→Use the same exact-reference form in other advertised logical Evidence inputs,
   483→including optional sources, arrays and nested sources across domains. Each
   484→source can independently be inline or retained; preserve its source identity,
   485→coverage, partial facts and unknowns. A summary or inspection page has its own
   486→Evidence ID: use `normalized_result.parent_evidence_id` when the consumer needs
   487→the complete source. For portable CLI follow-ups, commands advertising
   488→`--evidence-bundle` resolve references from that selected exported bundle.
   489→See [Evidence composition](references/evidence-workflows.md) for scope and
   490→recovery; file selectors are supported only where explicitly advertised.
   491→Page module identities and select the returned `node_id` before requesting an
   492→item; a single file path can represent several graph roles. Do not repeat an
   493→identical analysis or rejected call without a changed input or resolved blocker.
   494→Recheck session state when a lifecycle change makes that status useful.
   495→Make a focused follow-up only when the
   496→returned result leaves a specific question unanswered.
   497→
   498→If MCP reports `resource_constraint` with `details.resource: "transport"`, call
   499→`inspect_analysis_view` with its reported same-session Evidence reference for a
   500→summary, one section/module, or a stable page. Use `trace_application_feature`
   501→once a seed is known, or call `export_evidence_bundle` to write the complete
   502→session to a selected path. The analysis remains complete in the ledger; avoid
   503→repeating it merely to request the same oversized response. Complete CLI JSON
   504→output also streams without a single MCP frame.
   505→
   506→When the retained parent ID is unknown, use `get_evidence_bundle` with
   507→`detail: "summary"` and exact filters for operation, target SHA-256,
   508→analysis-profile digest or canonical procedure address. Select its returned
   509→Evidence ID for the next view instead of requesting the complete bundle. When
   510→that record has no supported view (for example an annotation), read it with
   511→`detail: "records"` and an `evidence_id` filter; `missing_evidence_links`
   512→names linked sources this session does not retain.
   513→`retention: "complete-record"` means the whole record is stored; native
   514→value-flow truncation and unknown metadata remain separate. For an exported
   515→portable bundle, use `rea inspect-evidence-bundle` with JSON containing `path`,
   516→`detail: "summary"` and the same `filters`. Reading that file still requires
   517→validating its full contents within the local memory budget.
   518→
   519→A client can also truncate a successful tool result without a REA transport
   520→error. Treat that preview as incomplete; use the retained parent ID for smaller
   521→views or export when the full record is needed. Do not parse the preview as
   522→canonical JSON or repeat the producer. For JavaScript, read the
   523→[module-view and trace recipes](references/javascript-applications.md) before
   524→drilling into a large graph; a broad bidirectional trace can expand unrelated
   525→containment relationships even after summary analysis.
   526→
   527→Every conclusion must distinguish observations, inferences, and unknowns. Cite
   528→Evidence IDs, preserve limitations and incomplete coverage, and never imply
   529→that static analysis observed execution. Runtime requests execute the declared
   530→target and lifecycle; do not broaden the target or action beyond those fields.
   531→
   532→Within the user's requested investigation, call available analysis tools
   533→directly. REA does not require permission grants or per-call approval flags.
   534→The agent client can independently require approval. Follow the declared request
   535→scope and the host's actual access requirements; use the recovery guide for an
   536→observed client-policy rejection.

   538→## Plan broader investigations
   539→
   540→For requests that span multiple features or subsystems, use a staged workflow:
   541→
   542→1. Turn the request into a checklist of questions and the evidence each answer
   543→   needs. Resolve target identity and constraints from the conversation and
   544→   workspace before asking for information again.
   545→2. Inspect the current REA session, artifact identity, saved analysis database,
   546→   bookmarks, and prior evidence. Reuse matching state; do not open duplicate
   547→   sessions or repeat identical analysis.
   548→3. Start with the smallest useful overview or inventory. Follow each question
   549→   from its entry point through relevant data and state changes to its result.
   550→   Batch related operations around a specific hypothesis, then expand only when
   551→   the returned evidence leaves a concrete gap.
   552→4. Inspect relevant packaged resources and configuration alongside code when
   553→   they affect the question. Use format-aware inventory and parsers; do not
   554→   infer behavior from filenames, strings, or layout alone.
   555→5. Corroborate a conclusion with the evidence type it requires. Use runtime
   556→   observation only when static evidence cannot answer the question and the
   557→   required host runtime and OS access are available. For JavaScript behavior,
   558→   run probes against the actual app through the available browser, Electron,
   559→   or process capture workflow.
   560→6. Decompose work into independent questions. When parallel workers are
   561→   available and the questions do not depend on one another, assign distinct
   562→   scopes, point workers to existing evidence, and ask them to return sources,
   563→   conclusions, and unresolved gaps. Otherwise, work sequentially.
   564→7. Keep a concise finding ledger linking each conclusion to Evidence IDs,
   565→   confidence/evidence type, search boundary, and remaining unknowns. Update
   566→   the shared index or investigation report so later passes can reuse results.
   567→
   568→Before finishing, revisit the original checklist. Mark each question as
   569→answered, partially answered, or unresolved based on its evidence; keep
   570→bounded negative searches bounded, and do not describe a broad investigation
   571→as complete while required questions remain open.

   594→## Finish the task
   595→
   596→Explain findings in plain language and tie them to returned evidence. When the
   597→user asks to build something, use normal coding tools and separate observed
   598→behavior from design choices. Close an opened native session with
   599→`close_binary` when its engine is no longer needed. Evidence references and Unknown
   600→history remain in memory on the same MCP connection. End the investigation with
   601→`reset_investigation`; supply `save_path` to checkpoint the complete bundle before
   602→clearing. Import the saved bundle to restore original references and Unknown
   603→history in a new process. Retention is bounded and is not automatic persistence.
